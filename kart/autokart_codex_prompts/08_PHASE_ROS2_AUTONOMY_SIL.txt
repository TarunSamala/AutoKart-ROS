AUTONOMOUS ELECTRIC GO-KART SIMULATOR
CODEX EXECUTION RULES

You are acting as the lead vehicle-dynamics, robotics, embedded, controls, safety, reliability, simulation, and software engineer.

This is not a game-only project. It is a research-grade, deterministic, configurable autonomous electric go-kart simulator that must eventually support software-in-loop, hardware-in-loop, real-kart calibration, and safety fault injection.

ENGINEERING PRIORITY
1. Human safety
2. Emergency stopping
3. Prevention of uncontrolled propulsion or steering
4. Predictable behaviour
5. Fault detection
6. Determinism and timing correctness
7. Physics and sensor correctness
8. Testability
9. Maintainability
10. Performance
11. Visual quality

MANDATORY ENGINEERING BEHAVIOUR
- Inspect the repository and run the complete existing test suite before modifying code.
- Preserve existing validated work.
- Do not perform destructive Git operations.
- Do not silently weaken tests, thresholds, or safety logic to make tests pass.
- Do not claim success because code compiles.
- Do not invent hardware specifications.
- Put provisional values in schema-validated configuration files.
- Record every assumption in docs/ASSUMPTIONS.md.
- Record important decisions in docs/ADR/.
- Use SI units internally.
- Keep world, vehicle, track, sensor, camera optical, and actuator frames explicit.
- Use deterministic fixed-step simulation and seeded random streams.
- Keep measurement time, processing completion time, delivery time, and consumer time separate.
- Keep operational sensor data separate from debug ground truth.
- Keep high-level computer, VCU, and independent safety layer separate.
- No actuator command may remain active indefinitely after communication loss.
- Every critical fault must have detection, safe response, latching/reset policy, and automated verification.
- Never claim ISO 26262, ASIL, automotive certification, or real-vehicle safety compliance.
- Mark example configurations:
  SIMULATION USE ONLY
  NOT APPROVED FOR DIRECT VEHICLE DEPLOYMENT

VERDICTS
Use only:
- APPROVED
- APPROVED_WITH_CONDITIONS
- REJECTED
- MORE_DATA_REQUIRED
- PROTOTYPE_TEST_REQUIRED

WORKFLOW
1. Audit repository and environment.
2. Run baseline tests and record exact results.
3. Identify interfaces affected by this phase.
4. Create a phase implementation plan.
5. Implement in small, testable increments.
6. Run unit, integration, regression, fault, determinism, and performance tests.
7. Update documentation and requirements traceability.
8. Produce the required final report.
9. Do not begin the next phase automatically.

EXTERNAL DEPENDENCIES
When a dependency is unavailable:
- Do not stop the whole phase.
- Implement clean interfaces and optional build flags.
- Add a deterministic fallback or mock where meaningful.
- Add installation and validation instructions.
- Mark tests requiring the dependency as explicit optional/integration tests.
- Never mark an unexecuted integration as passed.
PHASE 8
ROS 2 AUTONOMY INTERFACES, TIME SYNCHRONIZATION, TRAJECTORY CONTRACTS,
BASELINE CONTROLLERS, SOFTWARE-IN-LOOP, AND DETERMINISTIC REPLAY

PREREQUISITE GATE
Begin only after Phase 7 has implemented and tested:
- VCU state machine
- command source identity, counters, CRC/integrity, freshness, and timeouts
- watchdogs
- steering, brake, traction, and vehicle-response plausibility
- dynamic safety envelope
- controlled stop
- emergency stop
- independent safety-layer abstraction
- critical fault latching and reset policy

If these are missing, report BLOCKED or PARTIAL and implement only interfaces that do not bypass them.

OBJECTIVE
Create a ROS 2 integration layer that exposes the simulator to real autonomy software while preserving deterministic timing, safety boundaries, message age, and replayability.

The ROS 2 layer must not replace the internal simulator API. The simulator must continue to run headlessly without ROS 2.

REQUIRED DATA FLOW
simulator ground truth and sensor models
→ ROS 2 sensor publishers
→ perception/localization/planning software
→ trajectory or high-level motion command
→ ROS 2 command subscriber
→ command integrity/freshness adapter
→ VCU validation and dynamic safety envelope
→ actuator commands
→ simulated vehicle

3. SIMULATION CLOCK AND TIME

- measurement timestamps preserved from Phase 6
- delivery timestamps not substituted for capture timestamps
- replay with original timestamps
- time-jump detection
- reset/epoch policy
- no wall-clock dependence in deterministic mode

Define how ROS time maps to:
- simulation time
- sensor-local time
- capture time
- delivery time
- replay time

Tests:
- clock monotonicity
- pause freezes simulation time
- single-step advances exact fixed steps
- reset behaviour
- time jump rejected or explicitly handled
- replay produces identical timing

4. FRAME TREE
Publish and validate a frame hierarchy similar to:
map
→ odom
→ base_link or vehicle_body
→ sensor frames
→ optical frames
→ wheel frames
→ steering linkage frames

Requirements:
- explicit REP-compatible camera optical frame conversion where applicable
- static versus dynamic transforms separated
- no duplicate frame IDs
- quaternion normalization
- transform timestamps correct
- physical mounting transform separate from reported calibration transform
- frame graph validation command and tests

- sensor_msgs/JointState where appropriate
- nav_msgs/Odometry

- geometry_msgs/PoseStamped
- geometry_msgs/TwistStamped
- diagnostic_msgs/DiagnosticArray
- rosgraph_msgs/Clock

Create custom messages only when needed.

Required custom contracts may include:

- Trajectory
- TrajectoryPoint
- VcuState
- SafetyState
- ActuatorFeedback
- PowerState
- SensorHealth
- FaultEvent

Every safety-relevant message must include:
- protocol version
- source
- destination where applicable
- sequence counter
- generation or measurement timestamp
- validity duration
- units
- value ranges
- quality/validity
- fault flags
- configuration/calibration version
- integrity field where used by the simulated command protocol

Do not rely only on ROS transport reliability for command integrity.

6. QoS
Define per-topic QoS based on semantics.

Examples:
- camera and LiDAR: sensor-data profile, bounded queue
- IMU: low latency, bounded queue
- commands: reliable where appropriate, small depth, deadline/liveliness monitoring
- state and diagnostics: reliable, transient-local only where justified
- /clock: deterministic and documented

Test:
- lost messages
- slow subscriber
- queue overflow
- incompatible QoS
- stale command despite reliable transport
- liveliness loss

11. TRAJECTORY MESSAGE
Trajectory must contain time-parameterized points:
- relative or absolute time
- x, y, z
- heading
- speed
- acceleration
- curvature
- optional jerk
- path/track coordinate s
- validity
- frame ID

Validate:
- monotonically increasing time
- finite values
- bounded curvature
- bounded speed/acceleration
- frame consistency
- no duplicate points
- sufficient horizon
- not stale
- trajectory starts near current state within configured tolerance

Do not accept a spatial path as a complete trajectory without timing.

12. PURE PURSUIT CONTROLLER
Implement as a baseline, not as a safety layer.

Required:
- configurable lookahead
- speed-dependent lookahead option
- nearest/progress point handling
- closed-loop track support
- reverse disabled unless explicitly supported
- steering saturation
- steering-rate limit
- low-speed handling
- command timestamp and expiry
- debug outputs

Core geometry:
curvature_command = 2*y_local / lookahead_distance^2
or an equivalent documented formulation.

Tests:
- straight path
- constant-radius path
- closed-loop seam
- low speed
- lookahead beyond final point
- off-path recovery
- noisy localization
- steering saturation

13. STANLEY CONTROLLER
Implement:
delta = heading_error + atan2(k * cross_track_error, speed + softening)
with documented sign conventions and angle normalization.

Required:
- low-speed softening
- steering and rate limits
- direction/sign tests
- closed-loop support
- debug terms
- no divide-by-zero

Tests:
- straight convergence
- left/right sign
- circular tracking
- low speed
- large cross-track error
- noisy heading
- saturation

14. LONGITUDINAL CONTROLLER

- speed PID or PI baseline

- anti-windup
- output saturation
- torque/brake arbitration
- command rate and jerk limits
- standstill logic
- brake hold
- reverse disabled unless explicitly supported
- safety-envelope speed limit input
- VCU remains final authority

Tests:
