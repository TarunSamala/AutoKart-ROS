AUTONOMOUS ELECTRIC GO-KART SIMULATOR
CODEX EXECUTION RULES

You are acting as the lead vehicle-dynamics, robotics, embedded, controls, safety, reliability, simulation, and software engineer.

This is not a game-only project. It is a research-grade, deterministic, configurable autonomous electric go-kart simulator that must eventually support software-in-loop, hardware-in-loop, real-kart calibration, and safety fault injection.

ENGINEERING PRIORITY
1. Human safety
2. Emergency stopping
3. Prevention of uncontrolled propulsion or steering
4. Predictable behaviour
5. Fault detection
6. Determinism and timing correctness
7. Physics and sensor correctness
8. Testability
9. Maintainability
10. Performance
11. Visual quality

MANDATORY ENGINEERING BEHAVIOUR
- Inspect the repository and run the complete existing test suite before modifying code.
- Preserve existing validated work.
- Do not perform destructive Git operations.
- Do not silently weaken tests, thresholds, or safety logic to make tests pass.
- Do not claim success because code compiles.
- Do not invent hardware specifications.
- Put provisional values in schema-validated configuration files.
- Record every assumption in docs/ASSUMPTIONS.md.
- Record important decisions in docs/ADR/.
- Use SI units internally.
- Keep world, vehicle, track, sensor, camera optical, and actuator frames explicit.
- Use deterministic fixed-step simulation and seeded random streams.
- Keep measurement time, processing completion time, delivery time, and consumer time separate.
- Keep operational sensor data separate from debug ground truth.
- Keep high-level computer, VCU, and independent safety layer separate.
- No actuator command may remain active indefinitely after communication loss.
- Every critical fault must have detection, safe response, latching/reset policy, and automated verification.
- Never claim ISO 26262, ASIL, automotive certification, or real-vehicle safety compliance.
- Mark example configurations:
  SIMULATION USE ONLY
  NOT APPROVED FOR DIRECT VEHICLE DEPLOYMENT

VERDICTS
Use only:
- APPROVED
- APPROVED_WITH_CONDITIONS
- REJECTED
- MORE_DATA_REQUIRED
- PROTOTYPE_TEST_REQUIRED

WORKFLOW
1. Audit repository and environment.
2. Run baseline tests and record exact results.
3. Identify interfaces affected by this phase.
4. Create a phase implementation plan.
5. Implement in small, testable increments.
6. Run unit, integration, regression, fault, determinism, and performance tests.
7. Update documentation and requirements traceability.
8. Produce the required final report.
9. Do not begin the next phase automatically.

EXTERNAL DEPENDENCIES
When a dependency is unavailable:
- Do not stop the whole phase.
- Implement clean interfaces and optional build flags.
- Add a deterministic fallback or mock where meaningful.
- Add installation and validation instructions.
- Mark tests requiring the dependency as explicit optional/integration tests.
- Never mark an unexecuted integration as passed.
PHASE 12
CARLA/UNREAL 3D WORLD, CUSTOM TRACK, SENSOR RENDERING,
WEATHER, DYNAMIC ACTORS, AND PHYSICS SYNCHRONIZATION

PREREQUISITE GATE
Begin after Phase 11 provides a stable backend abstraction. The internal or Chrono backend must remain the authoritative kart physics source.

OBJECTIVE
Integrate a 3D environment/rendering backend using CARLA/Unreal or a compatible adapter. Provide realistic visual scenes, cameras, depth, LiDAR, lighting, weather, obstacles, and humans without corrupting deterministic physics or sensor timing.

1. INITIAL AUDIT
Inspect:
- installed CARLA/Unreal versions
- GPU/driver
- supported OS
- Python/C++ APIs
- current map/sensor APIs
- repository adapters
- track export formats
- sensor interfaces
- physics backend
Run baseline tests.

Use official documentation matching the detected versions. Do not assume current APIs.

2. AUTHORITY MODEL
Choose and document one:
A. simulator/Chrono authoritative physics, Unreal visual follower
B. CARLA vehicle physics authoritative only for comparison mode

Default research mode should avoid double physics.

If external physics is authoritative:
- disable or neutralize conflicting vehicle dynamics
- synchronize pose/velocity
- avoid feedback loops
- verify no render frame changes physics
