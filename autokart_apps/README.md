# AutoKart shared software milestone

## Implementation map

`autokart_perception.shared_core.AlgorithmCore` is the single Python implementation for graph geometry, local mapping, corridor and observed-ring planning, mission tracking, obstacle rejection, braking qualification, and the Pure Pursuit candidate. It calls the existing Phase 1 SciPy Delaunay, Gabriel, boundary, gate, centerline, curvature, and topology functions. Pure Pursuit comes from `kart_sim.autonomy`.

`autokart_perception.application.CoreRuntime` calls those modules directly. Its command line process has no HTTP dependency. LAB runs separately through `autokart_perception.lab_api.LabAdapter`; `/api/core/evaluate` delegates to the same `CoreRuntime`. If the LAB API or browser exits, CORE can still process samples or frames. There is no VCU transport in either new entrypoint. Every result sets `vehicle_authorized: false` and `published_to_vcu: false`.

The LAB `/shared` browser view is an extension of `phase_sim`. The world cones and kart physics are generated by the Python LAB process. `kart_sim.vehicle.PlanarBicycleKart` advances the kart. Sensor observations are formed from the simulated world and field of view. The odometry estimate is integrated from simulated speed and yaw rate; the Python algorithms receive that estimate rather than the world pose. The browser displays returned graph, path, and controller data; it does not calculate them. Existing `/` and `/demo` views remain legacy views.

## Run

From `/home/mark1/Desktop/autonomous_kart`:

```bash
./autokart_apps/run_core.sh
./autokart_apps/run_core.sh --source replay --input /absolute/path/to/recording
./autokart_apps/run_core.sh --source hp60c
./autokart_apps/run_lab.sh
./autokart_apps/run_tests.sh
python3 autokart_apps/verify_shared_http.py  # while LAB is running
```

The CORE default is one clearly labeled `SIMULATED` JSONL sample. `replay` reads existing Phase 1 recordings through `Replay` and `Pipeline`. `hp60c` uses the native HP60C bridge and checksum-bound orange-only detector; it retries disconnects and reports them without authorizing motion. No fresh pose provider is connected to live or replay modes yet, so those modes cannot yield a valid controller candidate. LAB serves its API on `127.0.0.1:8767` and the browser on [http://127.0.0.1:5173/shared](http://127.0.0.1:5173/shared). Stop LAB with Ctrl+C.

The equality command resets LAB state before each deterministic sample, invokes CORE as a separate process, and compares all geometry, planning, mission, controller, and authority fields with LAB's HTTP result.

The host used for this milestone already had Python 3.10, NumPy, SciPy, OpenCV, PyYAML, Pydantic, pytest, Node, and `phase_sim/node_modules`. For a new software-only Ubuntu checkout, install the two existing Python packages with `python3 -m pip install -e ./autonomy_stack_phase1/phase_01_perception -e ./kart`, then run `npm ci` in `phase_sim`. Those installation commands have not been verified on a clean system or on ARM64. Live HP60C additionally requires the existing vendor SDK and `phase_01_perception/build_native.sh`; consult the Phase 1 camera documentation before use.

## Input and output contract

Inputs use SI units. Cone `xy` is `base_link` X forward, Y left. Pose is in `odom`; a fresh pose estimate must be no older than 150 ms with position standard deviation at most 0.5 m. The local cone map is bounded to 256 entries and expires observations after 10 s. Timestamps are nanoseconds. The output includes an algorithm version, configuration SHA-256, reasons, full geometry, planning validity, mission state, and a diagnostic controller candidate. A valid candidate is **not** permission to drive.

`SKIDPAD` uses two colored observed cone rings for each loop. It requires adequate angular coverage, consistent inner and outer ring centers, and a plausible 2–3.8 m boundary width. The fitted centerline is an observed-map hypothesis, not a surveyed course. Lap progress uses the supplied pose estimate and directed winding; missing pose or an incomplete map withholds the path and lap claim. This remains a software candidate, not a qualified skidpad planner.

`BRAKING_TEST` requires an explicit simulated or measured braking capability and stop-zone distance. The LAB can use `SIMULATED` capability for diagnostics. No real vehicle braking capability is configured or inferred.

## Current boundary

The software comparison and UI launch pass on this x86_64 host. Raspberry Pi installation, ARM64 native SDK build, HP60C live frames, external odometry, ROS 2 publications, VCU feedback, independent E-stop, physical braking, watchdogs, and systemd startup have **not** been validated by this milestone. Real vehicle command transport is absent. See [VALIDATION.md](VALIDATION.md) for executed evidence and the next gate.
